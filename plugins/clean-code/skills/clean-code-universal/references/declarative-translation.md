# Clean Code — Declarative Translation Table

One row per rule. Open
[ch09 — declarative and config](../chapters/ch09-declarative-and-config.md) to **learn** the
mapping; open this to **apply** a rule you already know to the file in front of you.

**How to read it.**

- **Tier** is [ch01](../chapters/ch01-what-survives-translation.md)'s, the index of record. Tier 1
  rows need no translation — they are listed so the table is complete, and their Declarative
  column says what the rule looks at in a config file. A Tier 2 row names the construct that can
  be absent, and does not bind until you have found it.
- **`no construct — does not apply`** is a verdict, not a gap. Where a Tier 2 rule has nothing to
  bind to, that is the answer; an approximated rule is uncheckable and teaches the reader to
  discount the rules that do reach (ch01).
- **`Enforced by`** names a tool that exists or says `review only`. Nothing hypothetical.
- **A rename or a deletion here is a state operation**, so every cell that describes one carries
  what it costs. If a cell names a destructive or re-addressing operation without its qualifier,
  that is a defect in this file — the qualifier travels with the operation or the operation is not
  mentioned.
- **Version floors are stated inline**: `moved` **1.1+**, `optional()` **1.3+**, `terraform test`
  **1.6+**, `removed` **1.7+**, Helm `values.schema.json` and `type: library` **3.0+**, Rego v1
  **OPA 1.0+ / conftest 0.57+**, `CREATE OR ALTER VIEW` **SQL Server 2016 SP1+**.
- **`†`** marks a rule stated in its chapter that **ch01 gives no row** — a chapter-local framework
  or instrument. It is listed so the table matches the chapters, and it is not one of ch01's 39.

**Count.** 39 rows carry one of ch01's 39 rules, one each; 15 more are marked `†`. 54 rule rows.

## Names and values

Owned by [ch02](../chapters/ch02-names-and-magic-values.md). Seven ch01 rows, two `†`.

| Rule | Tier | Imperative / OO | Functional | Declarative (YAML/HCL/SQL/Bash) | Enforced by |
|---|---|---|---|---|---|
| **Intention-revealing names** | Tier 1 — a name | variable, field, class, method | binding, combinator | as written: keys, `metadata.name`, resource labels, job and step names, column names. **The cost is the rename, not the name.** An HCL label *is* the address, so renaming it carries a `moved` block (**1.1+**) or a `terraform state mv`, or the plan proposes destroy-and-create. A changed `metadata.name` under `kubectl apply` **creates a second object** and leaves the first live and unreferenced — delete the old one by name. A column rename is a contract change with every view, report and application naming it, and SQL has no rename-with-forwarding: add, backfill, migrate readers, drop, one per commit. | `review only` |
| **Name length proportional to scope** | Tier 1 — a name | local vs package-level | local binding vs export | `each.key` inside a `for_each` is fine; a root `local`, a values key every consumer sets, a view read across the schema earn the long name. A key in a schema you do not own cannot be renamed at all, so the intent goes in a comment (ch07). | `review only` |
| **One word per concept, never pun** | Tier 1 — a name | `get`/`fetch`/`retrieve` | one name per operation | one verb across job names, one noun across values keys — `timeoutSeconds` everywhere, never `timeout` beside it. The `app.kubernetes.io/name`, `/instance`, `/component` set is this rule already standardised for you. | `grep` finds the variants; `review only` for the verdict |
| **Searchable names** | Tier 1 — a name | constant over literal | constant over literal | this is the compiler you do not have: `grep` is the only find-all-callers these formats offer, so an unsearchable key, a bare `3` or a one-letter `locals` entry cannot be changed safely at scale. | `grep`; `review only` |
| **No noise words** (`Manager`, `Data`, `Info`) | Tier 1 — a name | `ProductInfo`/`ProductData` | same | `config:`, `data:`, `info:`, `common.yaml`, `utils.sh`, `main2.tf`. Usually the tell of aggregated responsibility, so it is ch05's rule showing up as ch02's evidence. | `review only` |
| **The name must include the side effects** | Tier 1 — a name | a `get` that also creates | a "pure" function that writes | a `check_config` script that rewrites the config; a CI job named `test` that also pushes; a `validate` stage that applies. The fix is usually to remove the effect rather than lengthen the name (ch03). | `review only` |
| **Magic values become named constants** | Tier 1 — a name | `SECONDS_PER_DAY` | named binding | `locals` in HCL — **the cheap one**: a `local` is not part of the module's interface, so introducing one is invisible to the plan and still gives `0 to add, 0 to change, 0 to destroy`. Also a Helm value, a CI `env:`. Hardcoded ARNs, account IDs, regions and CIDRs go here; a hardcoded account ID makes the module single-tenant. **SQL mostly has no constant construct**, and ch01 says state that rather than approximate: a lookup table joined by name, a generated constants file on the calling side, or an enumerated domain type. A floating tag is a magic value that changes without a commit — `node:latest`, `node:20`, `actions/checkout@v4`, `@main`, `version: "*"` are all mutable; pin the digest or the 40-character SHA and accept the bump bot you now need. | `hadolint` (untagged and `latest` bases), `kube-linter` (`latest-tag`); `conftest`/OPA where the literal sits in a known field; otherwise `review only` |
| **Don't repeat the container's name in its members** † | — (not a ch01 row) | `car.carMake` | record field | `resource "aws_s3_bucket" "logs"`, never `"logs_bucket"`: the address is already `aws_s3_bucket.logs`, so the suffix stutters at every use. SQL's `tbl_customer` and `vw_active` are the same defect as type prefixes. **Renaming an existing label to fix the stutter is a state operation**: it carries a `moved` block (**1.1+**) or a `terraform state mv`, or the plan proposes destroy-and-create — see *Intention-revealing names*. | `review only` — `tflint`'s `terraform_naming_convention` checks case and a regex, not whether a label repeats its type, and `sqlfluff` has no `tbl_`/`vw_` prefix rule |
| **Add context by enclosure, not by prefix** † | — (not a ch01 row) | class, namespace | module | put the names inside a well-named container — a Terraform module, a chart, a YAML mapping, a SQL schema — and prefix only as a last resort. Gratuitous context is the same mistake inverted. | `review only` |

## Units of work

Owned by [ch03](../chapters/ch03-units-of-work.md). Seven ch01 rows, one `†`. The unit per ecosystem:
module, chart, object, job, step, CTE, view, function, image, stage.

| Rule | Tier | Imperative / OO | Functional | Declarative (YAML/HCL/SQL/Bash) | Enforced by |
|---|---|---|---|---|---|
| **Do one thing = one level of abstraction below the name** | Tier 1 — a name | function, method | function | measured against the **name**, so it reaches an artifact nothing invokes: one manifest file bundling a Deployment, a Service and a ConfigMap does three things; a `deploy` job that also builds cannot be re-run after a flaky deploy without rebuilding; a 200-line query with five well-named CTEs passes where the same query nested four subqueries deep does not. | `review only` |
| **The TO-paragraph test** † | Tier 1 — a name | — | — | names no construct, so it runs verbatim: TO provision the audit log bucket, we create the bucket, apply the retention policy, and grant the reader role. If the paragraph needs *and then, separately, we also*, you have found the split point. | `review only` |
| **Size as a smell signal** | Tier 1 — a name | ≤ 20 lines | same | counted on the artifact, no call site needed: a 900-line values file, a 300-line template, a 600-line `main.tf`. The Java-era numbers do not transfer — 200 lines of Terraform is six or seven resources — but the signal does. Splitting is cheap for a consumer that globs a directory, costly for one reading a fixed path, and changes nothing about what is applied. | `yamllint` (line length), `sqlfluff` (`max_line_length`); file length `review only` |
| **Nesting depth as a smell signal** | Tier 2 — a branching construct | depth ≤ 2 | same | **absent in a bare manifest; supplied by Helm/Jinja templating, HCL `dynamic`, Bash, SQL `CASE`.** The number counts control flow the author chose, not indentation: a minimal clean Deployment nests **seven** levels on schema-imposed structure alone, so reported as raw indent depth the signal fires on every object that exists. Where the construct is there it bites — a four-deep `{{ if }}` / `{{ range }}` / `{{ if }}` / `{{ with }}` chain in a template, three nested `dynamic` blocks in HCL, a `case` inside a loop inside a conditional in Bash. | `review only`; `shellcheck` and `sqlfluff` see their own languages' nesting |
| **Input count and the arity budget** (0 · 1 · 2 · 3 avoid · 4+ never) | Tier 2 — a parameter list | argument list | argument list | **three parameter lists here**: a module's `variable` blocks, a chart's `values.yaml` surface, a Bash function's positionals. Fifteen variables is a module doing several things; the parameter-object move is one `object({...})` variable with `optional()` attributes (**Terraform 1.3+**). Each input multiplies the case matrix the `.tftest.hcl` files and the policy suite must cover, so arity is a verification budget. | `review only` (count them); the matrix is paid for in `terraform test` (**1.6+**) |
| **No flag inputs** | Tier 2 — a parameter list | `render(true)` | boolean argument | `create_bucket = true` driving a `count` is ch03's flag input — two modules merged. `deploy prod api true 30` is the same defect in Bash, worse because positionals are unnamed at the call site. A values key that switches a chart between two shapes is the Helm form. | `review only` |
| **No output arguments** | Tier 2 — a parameter list | `appendFooter(report)` | n/a — values are immutable | **HCL, and YAML through a chart's values surface: the construct exists — a module's `variable` blocks are the parameter list (ch01) — but neither can express a write-through, so the defect is unrepresentable.** A `variable` is immutable inside the module, and a module answers through `output`. **Bash has the construct**: a function handed a variable *name* and assigning through a nameref (`local -n`, **Bash 4.3+**) or a global is exactly the output argument — write to stdout, or set one documented global. | `review only` |
| **Command/query separation** | Tier 2 — a return value | `if (set("username", "bob"))` | effect type vs pure value | **A manifest returns nothing, so there is no construct and the rule does not apply** — applying a manifest cannot violate it, and ch03 declines to invent a manifest-shaped version. **An HCL module has the construct** — its `output`s are a return value (ch01) — **and is a command and a query by design**, so the rule is not actionable on the module itself. Where a return does exist it binds: a Bash function that echoes a value and also writes a file is unreadable at the `$(...)` that captures it; a SQL function that mutates and returns a row. | `review only` |

## Duplication

Owned by [ch04](../chapters/ch04-duplication-and-abstraction.md). Two ch01 rows, one `†`.

| Rule | Tier | Imperative / OO | Functional | Declarative (YAML/HCL/SQL/Bash) | Enforced by |
|---|---|---|---|---|---|
| **Duplication and the same-reason-to-change test** | Tier 1 — a name | extract a method or class | extract a function | name a change you expect and say whether it lands on both. **The DRY tools, by what they cost**: HCL `for_each` or a module; a Helm library chart (`type: library`, **Helm 3.0+**); a reusable workflow or composite action; a SQL view; a shared Docker base stage; and YAML anchors (`&base` / `*base` / `<<: *base`), which are the weakest — an alias reaches only within one `---` document, `<<` is a YAML 1.1 extension rather than YAML 1.2 core, and most tools that read a file and write it back emit the **expanded** form, so the first machine edit deletes the abstraction and leaves the duplication. **Cost of the HCL move**: converting unkeyed resources — or a `count` — into a keyed `for_each` **changes the instance keys**, so it needs **one `moved` block per instance** (**1.1+**), not one per resource; and an unkeyed `count` is index-addressed, so removing a middle element re-indexes every later one and plans destroy-and-create for each. | a copy-paste detector (`jscpd`) finds the literal repeats; the test itself is `review only` |
| **Extract until you cannot** † | — (not a ch01 row) | stop at `addOneToCounter` | same | stop when the next extraction's name would only restate its body. A module whose body is one resource and whose every argument is `var.x` is past that line — name the decision it should be making, or remove it, which re-addresses every resource inside it and so needs a `moved` block (**1.1+**) or a `terraform state mv`, or the plan proposes destroy-and-create. | `review only`; `terraform plan` prices the removal |
| **The bad-abstraction caveat, and the cross-domain exception** | Tier 1 — a name | two modules, two domains | same | resemblance is not a shared reason to change: two charts that merely look alike stay two charts. **What extraction couples**: a library chart couples release cadence, so each fix is a version bump in every consumer's `Chart.yaml`; a shared workflow referenced by a branch ref changes under **every** caller at once, with no consuming repository changed and no consuming reviewer present; a shared base stage couples rebuild cadence. **Undoing a shared view is priced by dialect**: PostgreSQL's `CREATE OR REPLACE VIEW` cannot rename, reorder or drop columns and its `DROP VIEW` defaults to `RESTRICT` (both checked on 18.6), so the refactor arrives as a loud refusal and `CASCADE` is what makes it destructive — enumerate the dependents first; MySQL's and Oracle's `CREATE OR REPLACE VIEW` and SQL Server's `CREATE OR ALTER VIEW` (**2016 SP1+**) replace the definition wholesale and their `DROP` does not refuse, so the same edit is silent there. | `review only` |

## Structure and dependencies

Owned by [ch05](../chapters/ch05-structure-and-dependencies.md). Nine ch01 rows, two `†`. This is where
most of the `does not apply` verdicts live, and they are the honest answer rather than a gap.

| Rule | Tier | Imperative / OO | Functional | Declarative (YAML/HCL/SQL/Bash) | Enforced by |
|---|---|---|---|---|---|
| **SRP — one, and only one, reason to change** | Tier 1 — a name | class | module | the only SOLID row needing no type system, which is why it reaches YAML. Describe it in 25 words without "and": one concern per image (app plus cron plus sidecar proxy is three, so it is rebuilt three times as often as any one of them needs); one chart per workload; a schema per domain, since a view joining reporting and billing has two reasons to change; `build-and-push-and-notify` failing the naming test. A toolchain and a runtime have different reasons to change, which is what a multi-stage build splits — and a stage you never `COPY --from` never ships. | `review only` |
| **The extraction loop** † | — (ch05 states it is not a ch01 row) | extract → promote locals → cohesion drops → split | same | reads identically on a Terraform module's `locals`: list the module's state down one axis and its units across the other, and a block touching a disjoint subset is the split. | `review only` |
| **Data vs. behaviour, and the axis-of-change test** | Tier 2 — an object | choose by the axis you grow along | same | **no object — does not apply.** A manifest, a values file and a module are data structures, so the choice has already been made for you: new operations over the same shapes are cheap, new *kinds* of thing are the expensive axis. | n/a — the rule does not apply |
| **Law of Demeter and tell-don't-ask** | Tier 2 — an object | train wreck of accessors | pipelines are not chains | **no object — does not apply.** ch05 is explicit that `var.tags.owner` and `.spec.template.metadata.labels` are **not** violations, nothing in either chain being an object. A long path is a naming and coupling question (ch02, ISP), never this row. | n/a — the rule does not apply |
| **OCP — open for extension, closed for modification** | Tier 2 — a substitutability mechanism | interface + implementations | sum type + dispatch | **HCL, SQL and a bare manifest supply no substitutability mechanism — does not apply.** A `lookup` on a `type` attribute is not a variant table awaiting a contract. **Bash is the exception ch05 names**: duck typing counts, so a command name passed in and invoked is a substitutability mechanism — unchecked by anything, so review and tests are all you have. | `review only` in Bash; elsewhere n/a — the rule does not apply |
| **LSP — the subtype is accepted unchanged** | Tier 2 — a substitutability mechanism | subclass | instance of a class/trait | **HCL, SQL and a bare manifest supply no substitutability mechanism — does not apply.** ch01 uses exactly this case: a Helm chart has no subtype, so LSP does not apply, and that is the answer rather than a prompt to invent one. **Bash keeps it as a convention** (ch05): duck typing *is* substitutability, so a function swapped in behind an existing call site must take the same arguments and return the same statuses — nothing declares that and nothing checks it, so the breach lands at run time. | `review only` in Bash; elsewhere n/a — the rule does not apply |
| **ISP — no client depends on what it does not use** | Tier 2 — a declared interface | interface per capability | narrow signature | **the Tier 2 row with the most purchase here.** The declared interfaces are a module's `output` blocks, a chart's values keys and a view's column list. A view defined `SELECT *` publishes every column of every base table, and in PostgreSQL the `*` is expanded **when the view is created**, so a column added to the base table afterwards never appears in it (checked on 18.6). `terraform_remote_state` reads the other root's **entire** state — the widest interface there is — and needs read access to a file that usually holds secrets in plaintext; publish one value instead. **The cost is asymmetric**: adding an output is free, removing one is a plan-time error in **every** root module referencing `module.x.y`, and renaming or removing a values key fails **silently**, because Helm merges a user's unknown keys without complaint, unless a `values.schema.json` (**Helm 3.0+**) makes it loud — treat a removal as breaking. | `terraform plan` (a removed output breaks referencing roots); `helm lint` / `helm template` against a committed `values.schema.json`; `review only` for the narrowing itself |
| **DIP, with injection and a consumer-shaped abstraction** | Tier 2 — an injectable abstraction | constructor injection | pass the function in | **the row that loses least.** Pass the value in as a `variable` rather than reading `data "aws_vpc"` inside the module: a `data` block resolves at plan time against whatever account the credentials point at, so a module that reads its own dependencies can be planned neither against a fixture nor anywhere that object is absent — which ch08 records as a **design** finding, not a testing one. In SQL the view is the injectable indirection: the consumer names the shape it needs and the table underneath can be partitioned, renamed or replaced. In Bash, take the command or the path as a parameter. | `terraform test` (**1.6+**) — a module reading its own `data` cannot be planned against a fixture; `review only` |
| **Polymorphism instead of a type switch** | Tier 2 — a substitutability mechanism | one switch creating the variants | pattern match | **HCL, SQL and a bare manifest supply no substitutability mechanism — does not apply.** A `CASE` over a `type` column and a `lookup` on a `type` attribute are not type switches awaiting polymorphism, and one module per variant is SRP, not this row. **Bash keeps it as a convention** (ch05): a `case $kind in` growing a branch per variant is the real thing, and the fix is one function name dispatched per variant — a convention only tests and review enforce. | `review only` in Bash; elsewhere n/a — the rule does not apply |
| **Concurrency as a decoupling concern** | Tier 2 — a thread | keep concurrency code separate; limit shared data | same | **Terraform, CI and a bare manifest: no thread — does not apply.** The schedule comes from your declared dependency graph, so two units racing on one external object are an **undeclared dependency**, not a concurrency defect: declare it (`depends_on`, a job's `needs`) and the graph serialises them. **Bash supplies what the rule needs** — `&` with `wait` is a process rather than a thread, but it is concurrent execution over shared state, the state being the filesystem — so the corollary reads as one output path per background job. | `review only` |
| **Boundaries — wrap a foreign vocabulary and translate it** † | — (ch05 states it is not a ch01 row) | adapter over the third-party type | adapter | the provider, chart and base image you did not write. The wrapper that actually **translates** is a thin internal module exposing your own variable names over the upstream one, so an upstream rename is one file's change rather than every root's. Pinning is the adjacent discipline and translates nothing: an unpinned `required_providers` entry lets the next `terraform init -upgrade` change your plan with no change to your configuration. **Commit `.terraform.lock.hcl`**, or each machine resolves its own; child modules state a floor and the root pins, because two children pinning different exact versions leave nothing resolvable. | `terraform init` verifies the lock file's hashes; `review only` for the wrapper |

## Failure

Owned by [ch06](../chapters/ch06-failure.md). Two ch01 rows, one `†`.

| Rule | Tier | Imperative / OO | Functional | Declarative (YAML/HCL/SQL/Bash) | Enforced by |
|---|---|---|---|---|---|
| **Exception and failure-propagation mechanics** | Tier 2 — an exception | `throw` / `catch`, one transaction scope | `Result`, `Either`, a typed error arm | **YAML, HCL, Bash, CI and Dockerfile supply no exception**, so there the rule's *prohibition* — raise rather than return a code — has nothing to prefer, and what survives is the two halves that need none: **carry the operation that failed**, and **never swallow**. HCL: `validation`, `precondition` and `postcondition` **abort** rather than propagate, and `try()`/`can()` **suppress** rather than catch — a `try()` round a lookup to quiet a plan moves the error from plan time, where it is a message, to apply time, where it is a wrong resource. Bash, CI and Dockerfile propagate by **exit code**: `set -euo pipefail`, a distinct non-zero code per case and a stderr line naming the command and its input. `set -e` does not fire for a status consumed by `if`, `&&`, `\|\|` or `!`, and `local x=$(cmd)` hides `cmd`'s status behind `local`'s own success — a bare `x=$(cmd)` does not, so declare and assign on separate lines. A GitHub Actions `run:` step is `bash -e {0}` by default on Linux and macOS runners, which is **not** pipefail; declare `shell: bash` or set `defaults.run.shell` once. SQL aborts the statement, and **what unwinds is dialect-specific**: PostgreSQL has transactional DDL (checked on 18.6), while MySQL and Oracle commit implicitly on DDL, so a migration cannot be wrapped there and a half-finished one stays that way. A bare manifest has **no mechanism of its own** — its failure design is `readinessProbe`, `restartPolicy` and admission. **Never swallow**: `\|\| true`, `2>/dev/null`, `continue-on-error: true`, `allow_failure: true`. **Adding `set -euo pipefail` to an existing script changes behaviour at every step that used to fail quietly**, so read what currently fails first and land it as its own commit (ch10). | `shellcheck`, `actionlint`, `terraform validate`, `kubectl apply --dry-run=server` |
| **Wrap a foreign failure vocabulary** † | — (ch06 states it is not a ch01 row of its own) | one handler over three | one error type at the boundary | ch05's boundary technique applied to failure; the wrapper translates and does nothing else. In configuration that is the thin internal module over the provider's vocabulary. | `review only` |
| **Absent-value handling and special-case objects** | Tier 2 — an absent-value sentinel | never return or pass null | `Option`, `Maybe`, empty collection | **the one Tier 2 row a bare manifest supplies the construct for** (ch01). HCL: an argument set to `null` is the same as omitting it, so a `null` travelling through a module `variable` into a resource argument is precisely "never pass a sentinel"; the Special Case analogue is a `variable` with a real default, or `optional(type, default)` inside an object type (**Terraform 1.3+**). **Kubernetes differs, and it costs live configuration**: in a strategic-merge patch a `null` **deletes** the field rather than leaving it unset, so an absent key and a `null` key are not interchangeable and writing one where you meant the other removes configuration from the live object. SQL: `NULL` is three-valued everywhere, so `WHERE status <> 'closed'` silently drops the rows where `status IS NULL` (checked on PostgreSQL 18.6). | `terraform validate` plus a `variable` `validation` block; `kubectl diff` (needs a cluster); `review only` for the SQL half |

## Comments and formatting

Owned by [ch07](../chapters/ch07-comments-and-formatting.md). Five ch01 rows, two `†`.

| Rule | Tier | Imperative / OO | Functional | Declarative (YAML/HCL/SQL/Bash) | Enforced by |
|---|---|---|---|---|---|
| **The rename test** † | — (not a ch01 row) | a comment is a naming suggestion | same | **the one place this test cannot be run**: you do not own these names. You cannot rename `terminationGracePeriodSeconds`, so where the schema's key cannot carry the intent the comment is the only carrier. Everywhere you *do* own the name, rename and delete the comment. | `review only` |
| **Comments: the default is don't, plus the legitimate kinds** | Tier 1 — a name | legal, intent, warning, amplification, TODO-with-a-plan | same | the surviving kinds earn their keep here: **amplification** beside a SHA pin — `actions/checkout@<40-char sha>  # v4.1.1` — and **warning of consequences** above anything whose obvious edit is a state operation. A TODO with a stated plan is findable by grep and is never a licence to leave the bad configuration. | `review only` |
| **No commented-out code, journals, bylines or banners** | Tier 1 — some verification | delete on sight; source control remembers | same | the restatement above `port: 8080`, the dated journal line, the byline, the `# --- networking ---` banner. **Commenting out a Terraform resource is not a pause, it is a deletion**: gone from the configuration, still in state, so the next plan proposes to destroy the live object. Worse in configuration than in code, because no reader can tell whether the block was ever applied. | `terraform plan` shows the destroy; the deletion itself is `review only` |
| **Delete dead code** | Tier 1 — some verification | unreachable branch, uncalled utility | same | **dead configuration is decommissioned, not deleted, and the two platforms fail in opposite directions.** Removing a Terraform block plans a **destroy** of the live object — **and so does a bare `removed` block, which by default drops the resource from state *and destroys the real object*. To stop managing something without deleting it the block must carry `lifecycle { destroy = false }` (Terraform 1.7+)**; `terraform state rm` is the other way. Removing a Kubernetes manifest from the repo does **nothing** to the cluster unless something prunes, so the object stays live, unowned and unreviewed — **delete it by name**. `kubectl apply --prune` is not a peer remedy: on v1.33.9 its own help calls it alpha, it should be used with `-l` or `--all`, and it covers only objects made by `apply` or `create --save-config`, so it skips controller-, operator- and Helm-owned objects while still deleting every applied object in that selector your file set no longer declares. `moved` blocks become dead configuration only once **every** workspace has applied. | `terraform plan`, `kubectl diff`; `review only` |
| **Formatting is tooling's job, and the team's style wins** | Tier 1 — some verification | one formatter, config committed, run in CI | same | `terraform fmt`, `shfmt`, `sqlfluff` — whose `dialect` setting is part of the committed style, because the linter cannot parse your SQL until you tell it whose SQL it is — `yamlfmt`/`prettier`, and `hadolint`, since Dockerfile has a linter and no canonical formatter. `terraform fmt` aligns consecutive `=` as a rule, so what is prohibited is hand-alignment as a judgment call. **Reformatting is not always free here**: a `RUN` instruction's text is part of that layer's build-cache key, so re-wrapping it rebuilds that layer and every layer below; the common Helm `checksum/config` annotation hashes the **rendered** ConfigMap, so a template reformat that changes the render rolls the Deployment; and in YAML quoting is semantic — under the YAML 1.1 resolver that PyYAML and other widely used loaders still implement, unquoted `no`, `on` and `22:30` resolve to `false`, `true` and `1350`. Format anyway, as its own commit. | `terraform fmt -check`, `shfmt -d`, `sqlfluff lint`, `yamllint`, `hadolint` |
| **Vertical ordering: newspaper rule, related things close** | Tier 1 — a name | entry point first, helper below its first caller | same | **the one formatting decision no tool makes for you**, and `terraform fmt` never reorders or renames, so it stays yours: the object a reader came for at the top and what it depends on below, a pipeline's stages in execution order rather than alphabetical, a Terraform `output` beside the resource behind it. **Dockerfile layer ordering is this rule with a measurable runtime cost** — copy the dependency manifest and install before the source, because a changed layer invalidates every layer after it, and backwards every one-character source edit reinstalls every dependency. | `review only` |
| **File and line size figures** † | Tier 1 signal; the numbers are Java-era | ~200 lines typical, 500 upper, ≤ 120 columns | same | the signal transfers, the numbers do not: 200 lines of Helm values is unremarkable and 200 lines of Terraform is six or seven resources, because structure rather than statements fills the lines. Set them per ecosystem in the formatter config, and do not split closely related concepts across files without a reason. | `yamllint` (line length), `sqlfluff` (`max_line_length`); file length is `review only` |

## Verification

Owned by [ch08](../chapters/ch08-verification.md). One ch01 row, three `†`.

| Rule | Tier | Imperative / OO | Functional | Declarative (YAML/HCL/SQL/Bash) | Enforced by |
|---|---|---|---|---|---|
| **The verification ladder** † | — (ch08 states it is not a ch01 row; a derivation) | the runner is rung 1 | same | seven rungs by the strength of the claim a green result licenses: unit → integration → contract → policy → plan/diff → schema → lint. **Own the highest the ecosystem gives you, and never claim a rung you do not run**: `fmt` is not `validate`, `validate` is not a plan (it contacts neither providers nor state), a plan is not a policy suite, a policy suite is not an apply, and an apply is the change rather than a check. CI pipelines have **no plan rung** at all, so independence is bought by gating the pipeline's effects. **A policy gate must be pointed at its own namespace**: `conftest test` evaluates `main` by default, so a policy in `terraform.audit` with no `--namespace` or `--all-namespaces` matches nothing, prints nothing and **exits 0** — a green gate that ran no rules. Rego v1 needs **OPA 1.0+ or conftest 0.57+**. | `conftest`/OPA, Sentinel, Checkov, `terraform plan`, `kubeconform`, `kube-linter`, `tflint`, `shellcheck`, `hadolint`, `actionlint`, `yamllint` |
| **Automated tests, TDD's three laws, F.I.R.S.T.** | Tier 2 — a test runner | the runner, red-green-refactor | same | **the runners that exist here**: `terraform test` (**1.6+**, `.tftest.hcl` files with `run` blocks — a real red-green loop, so write the `assert` first), `helm unittest`, `bats`, `pgTAP`/`tSQLt`/dbt, `container-structure-test`. **Where none exists — a bare manifest, a CI pipeline — the row does not apply**, and the honest red step is a policy suite: write the `deny`, run it against today's plan, watch it fail, then change the configuration. **What costs F and I**: `terraform test` with `command = apply` creates real objects and destroys them at the end of the file, so it is neither Fast nor Independent and leaves objects behind when the teardown itself fails, while `command = plan` creates nothing (it still reads, so it needs credentials); `EXPLAIN ANALYZE` **executes** the statement, so on a write it must be wrapped in a transaction you roll back; `kubectl apply --dry-run=server` runs the real admission chain and persists nothing, while `--dry-run=client` reaches neither admission nor server-side validation and is not offline either — on kubectl **v1.33.9** it fails without cluster access even with `--validate=false`; `bash -n` parses and does not execute, so it catches nothing semantic. | `terraform test` (1.6+), `helm unittest`, `bats`, `pgTAP`, `tSQLt`, dbt, `container-structure-test` |
| **Build-Operate-Check** † | — (ch08 states it is not a ch01 row) | arrange, act, assert | same | a `.tftest.hcl` `run` block is `variables` / `command` / `assert`; a Rego policy is the input document / the expression reading it / the `deny` it produces; a `bats` case is `setup` / the invocation / the assertion on `$status`. | `review only` |
| **One concept per check** † | — (ch08 states it is not a ch01 row) | minimise asserts per concept | same | the tell is a reassigned shared subject — build, assert, rebuild, assert again is two concepts wearing one name, and the second failure hides behind the first. A `deny` rule covering two unrelated invariants reports one message for two findings. | `review only` |

## Improving existing code

Owned by [ch10](../chapters/ch10-improving-existing-code.md), plus ch01's own Beck row. Six ch01
rows, three `†`. Every step below is a state operation, and a reverted commit does not restore a
destroyed object.

| Rule | Tier | Imperative / OO | Functional | Declarative (YAML/HCL/SQL/Bash) | Enforced by |
|---|---|---|---|---|---|
| **Beck's four rules as the conflict resolver** (rule 1 generalised) | Tier 1 — a name + some verification | tests pass → no duplication → expresses intent → fewest units | same | rule 1 is whatever verification you have: an empty diff, a clean schema check, a green policy suite, a quiet linter. A design that does not verify is not simple. Rule 4 never overrides 1–3 — do not merge two well-named modules to have fewer of them. | whichever rung you own: `terraform plan`, `kubectl diff`, `kubeconform`, `conftest`, a linter |
| **Write it dirty, then clean it** | Tier 1 — some verification | draft, then shape it in review | same | build the verification **while** you build the mess. The cheapest rung to build first is a golden render: commit today's `helm template` / `kustomize build` / `terraform show -json tfplan` output and require every structural change to leave it unchanged — a pure structural refactor renders identically, so a one-line diff is a real finding. | a committed golden render in CI; `helm template`, `kustomize build` |
| **Tiny steps under green verification** | Tier 1 — some verification | green suite → extract → re-run | same | green → skeleton → migrate one use → re-run → fix any break before anything else → expect to undo earlier steps. **Two traps this format adds.** (1) A new module *directory* nothing calls is genuinely inert; a new `module` **block** is not a skeleton at all — it creates every resource inside it on the next apply, and it bills. The declarative equivalent of an unused class is an uncalled definition, never an added instance. (2) Migrating one use **renames an address**, so it carries a `moved` block (**1.1+**) or a `terraform state mv`, or the plan proposes destroy-and-create; a resource-level `moved` carries every instance with its key intact, and it is when the **keys** change — `count` to `for_each`, or separate resources folded into one keyed resource — that you need one block per instance. The gate is `0 to add, 0 to change, 0 to destroy`; `must be replaced` on a stateful object is a stop, not a warning. Diff the plan JSONs, never the terminal output. Keep the `moved` blocks until **every** workspace has applied, or one that has not will read the resource as new and propose destroy-and-create. `terraform state mv` by hand edits state immediately, appears in no diff and gets no review — back up with `terraform state pull` first; a `moved` block is the reviewable form. | `terraform plan -out=tfplan` then `terraform show -json tfplan`, diffed as JSON; `kubectl diff`; a golden render |
| **The stop rule** | Tier 1 — a name | N parallel edits per new case | same | in configuration N is usually visible in the file list: a new environment that means editing the module, the root, the tfvars and the pipeline matrix is N = 4; a new service that means a Deployment, a Service, an Ingress and a CI job is N = 4. That is a chart or a module trying to be born. N is the measurement; "it feels messy" is not. | `review only` |
| **Boy Scout Rule** | Tier 1 — some verification | one rename, one extraction, per check-in | same | **the cheapest Boy-Scout step HCL has is a `locals` extraction** — a `local` is not part of the module's interface, so it is invisible to the plan and still gives `0 to add, 0 to change, 0 to destroy`. **An opportunistic rename is not free**: a Terraform label *is* the address, so a Boy-Scout rename carries its `moved` block (**1.1+**) or it waits for a commit of its own. Keep the cleanup out of the behaviour commit either way, so that when the apply goes wrong you can revert exactly one thing. | `terraform plan`; `review only` |
| **LeBlanc's Law — later equals never** | Tier 1 — some verification | the cleanup not in this change will not happen | same | if it genuinely cannot be in this change it is a tracked work item, not a mental note. The two that rot longest here are a `moved` or `removed` block left behind after every workspace has applied, and the orphaned object you meant to delete by name. | `review only` |
| **First make it work, then make it right** † | — (not a ch01 row) | two phases, sequential, neither optional | same | doing both at once is how a behaviour change and a structural change share one commit — which in configuration makes the **plan unreadable**, because you can no longer tell which half of the diff was supposed to be empty. | `review only` |
| **Prefer structure that communicates over a parameter that merely enforces** † | — (ch10 states it is not a ch01 row) | a constraint the reader can see | same | `depends_on` enforces an ordering and explains nothing, so the next person deletes it; passing the other module's `output` in as an input enforces the same ordering **and** shows why, because the dependency is now in the data flow. The same argument is DIP's in ch05. | `review only` |
| **Most of a refactor is deletion** † | — (not a ch01 row) | a refactor that only adds migrated nothing | same | in code the un-migrated old path is dead code; in configuration **both paths are applied** — two sets of objects, two bills and two writers to the same external thing. | `terraform plan`, `kubectl diff` |
