# Glossary — clean-code-dart

**3 Rs (readable, reusable, refactorable)** — the guide's stated quality standard; "This is not a style guide." (Ch 1)
**`??` (if-null operator)** — supplies a fallback for `null`; the short-circuit that a `const` default parameter replaces where possible (Ch 2)
**`@override`** — marks a member that overrides or implements a supertype member; on every override in the guide's Good examples (Ch 6)
**Abstract class** — `abstract class Shape { double getArea(); }`; can't be instantiated, may declare bodiless methods; the guide's interface (Ch 6)
**Abstraction level** — the altitude of a statement: orchestration (`tokenize(code)`) vs mechanics (`code.split(' ')`); one per function (Ch 3)
**`async` / `await`** — mark a function that returns a `Future` / suspend until a `Future` completes; preferred over `.then` (Ch 8)
**Bad abstraction** — a merge of things that don't vary together; "can be worse than duplicate code" (Ch 3)
**Callers above callees** — newspaper ordering of members: each caller directly above what it calls (Ch 10)
**Cascade notation (`..`)** — runs a sequence of operations on one object and evaluates to that object; replaces `return this` chaining (Ch 5)
**Composition** — holding a collaborator in a field instead of extending it; preferred over inheritance (Ch 5)
**`const`** — compile-time constant; the declaration for a named magic value known before run time (Ch 2)
**Constructor injection** — receiving a collaborator through the constructor (`required this.requester`) rather than building it inside (Ch 6)
**Coupling** — how much one module depends on another's details; "makes your code hard to refactor" (Ch 6)
**Coverage** — share of statements and branches exercised by tests; the guide's ideal is 100% (Ch 7)
**Dead code** — code no longer called; delete it, version history keeps it (Ch 3)
**Default parameter value** — fallback in the signature (`{String breweryName = '…'}`); must be a compile-time constant (Ch 2)
**Dependency Inversion Principle (DIP)** — high-level and low-level modules both depend on abstractions; details depend on abstractions (Ch 6)
**`dynamic`** — opts out of static type checking; the side-effects Bad example needs it so a `String` can become a `List` (Ch 3)
**Effective Dart** — the Dart team's style, usage and design guidelines; the guide's formatting authority (Ch 10)
**`Exception` vs `Error`** — by Dart convention, anticipated failures vs programming mistakes; `on Exception` lets `Error`s propagate (Ch 9)
**Explanatory variable** — a `final` naming a value read by position, e.g. `final city = address[1];` (Ch 2)
**`extends`** — inherit implementation and type; used for OCP's shapes and LSP's rectangles (Ch 5, Ch 6)
**`final`** — a variable assigned exactly once, at run time; stops reassignment, not mutation of the object (Ch 2, Ch 3)
**Flag parameter** — a `bool` argument selecting a code path; "tell your user that this function does more than one thing" (Ch 3)
**`fold<T>`** — `Iterable.fold`; accumulates into a type other than the element type, where `reduce` can't (Ch 3)
**`Future<T>`** — a value of type `T` available later; Dart's Promise (Ch 8)
**`Future.onError`** — handles a `Future`'s error in `.then`-style code; its handler result replaces the future's value (Ch 9)
**`group` / `test` / `expect`** — `package:test`'s grouping, test-case and assertion functions (Ch 7)
**`implements`** — take on a class's interface without its code; every member must be provided (Ch 6)
**Initializer list** — `: _name = name` after a constructor's parameters; sets fields before the body runs (Ch 4, Ch 6)
**Initializing formal** — `this.balance` in a constructor's parameter list; assigns the parameter straight to the field (Ch 4)
**Interface Segregation Principle (ISP)** — "Clients should not be forced to depend upon interfaces that they do not use" (Ch 6)
**Journal comment** — a dated change log in the source; use `git log` instead (Ch 11)
**Library privacy** — a leading `_` hides a member outside its library (usually its file), not merely outside its class (Ch 4)
**Liskov Substitution Principle (LSP)** — subtypes usable in place of their base type "without getting incorrect results" (Ch 6)
**`log(message, error:, stackTrace:)`** — `dart:developer` logging with the error and trace attached; Option 1 for a caught error (Ch 9)
**lowerCamelCase** — Dart's case for variables, constants, functions, methods and parameters (Ch 2, Ch 10)
**Mental mapping** — making the reader translate a short name (`l`) into the concept it stands for (Ch 2)
**Named parameter** — `{…}` in a signature, passed as `name: value`; the Dart answer to long argument lists (Ch 3)
**Negative conditional** — a predicate named for the negative (`isFileNotValid`), forcing `!` double negatives (Ch 3)
**Nullable type (`T?`)** — a type that admits `null`; records an optional value, e.g. `EmployeeTaxData? taxData` (Ch 2, Ch 5)
**`on Type catch (e, s)`** — typed catch clause; `on` filters by type, `s` is the `StackTrace` (Ch 9)
**Open/Closed Principle (OCP)** — "open for extension, but closed for modification" (Bertrand Meyer) (Ch 6)
**Polymorphism** — a subclass override replacing a conditional on type (Ch 3, Ch 6)
**Positional marker** — a banner comment (`/////…`) marking a section; noise (Ch 11)
**Predicate function** — a named `bool` function wrapping a condition, e.g. `isValidDartProgrammer` (Ch 3)
**`required`** — makes a named parameter mandatory; omitting it is a compile-time error (Ch 3)
**Searchable name** — a name you can grep; why magic numbers become `const`s (Ch 2)
**Side effect** — anything a function does besides take values in and return values out (Ch 3)
**Single concept per test** — one behaviour per `test`, grouped by unit (Ch 7)
**Single Responsibility Principle (SRP)** — "There should never be more than one reason for a class to change" (Ch 6)
**Spread literal** — `[...cart, item]`; builds a new list instead of mutating one (Ch 3)
**`StackTrace`** — where an error came from; the second `catch` parameter, passed on in every Good handler (Ch 9)
**Super parameter** — `required super.name`; forwards a constructor parameter to the superclass (Dart 2.17+) (Ch 5, Ch 6)
**Tear-off** — passing a function by name (`where(isActiveClient)`) instead of wrapping it in a closure (Ch 3)
**Type inference** — Dart deduces a declaration's type from its initializer; `const setupTimeInMinutes = 32;` is an `int` (Ch 2)
**Type test (`is`)** — `shape is Circle`; a chain of them is OCP's Bad shape (Ch 3, Ch 6)
**`UnimplementedError`** — what a stub throws; in an implementer, the guide's ISP smell (Ch 6)
**Unneeded context** — repeating the class name in its members (`carColor`) (Ch 2)
**UpperCamelCase** — Dart's case for classes, enum types, typedefs and type parameters (Ch 10)
**Vocabulary consistency** — one noun per entity: `getUser`, not `getUserInfo`/`getClientData`/`getCustomerRecord` (Ch 2)
**`where`** — `Iterable.where(test)`; lazily filters by a predicate (Ch 3)
