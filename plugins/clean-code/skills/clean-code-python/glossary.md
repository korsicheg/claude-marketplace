# Glossary — clean-code-python

**Abstract Base Class (ABC)** — Python's stand-in for an interface, via `abc.ABCMeta` + `@abstractmethod`; enforced at instantiation, not definition (Ch 7)
**Abstraction (DIP sense)** — the minimal behavioural contract a dependency requires, e.g. "has `.write(value)`" (Ch 8)
**`@abstractmethod`** — marks a member subclasses must implement before the class can be instantiated (Ch 7)
**`astuple`** — `dataclasses.astuple(config)`; unpacks a dataclass positionally (Ch 3)
**Bad abstraction** — a merge of things that don't vary together; "can be worse than duplicate code" (Ch 9)
**Behavioural subtyping** — LSP as semantics, not just types; from Liskov & Wing (1994) (Ch 6)
**Buffer shuffling** — the `seek(0)`/`read()`/`seek(0)`/`truncate()` cycle used to drain a `StringIO`; a DIP smell (Ch 8)
**Capability ABC** — a small ABC representing exactly one feature, e.g. `Loadable`, `Saveable` (Ch 7)
**Class attribute override** — a subtype reassigning an inherited class-level value, e.g. `content_type = "text/html"` (Ch 5)
**Closed to modification** — new behaviour required no edit to existing code (Ch 5)
**Coincidental duplication** — code alike today for unrelated reasons; will diverge, so leave it (Ch 9)
**Contract** — the type-level agreement at a seam, e.g. "produces a `str`" / "accepts a `str`" (Ch 4)
**Constructor injection** — supplying a value or collaborator through `__init__` instead of computing it internally (Ch 4, Ch 8)
**Cooperative `super()`** — a mixin calling `super()` to wrap the target's method rather than replace it (Ch 5)
**Data carrier** — a base holding the shared state contract that capability ABCs build on, e.g. `DataCarrier.data` (Ch 7)
**`@dataclass`** — decorator generating `__init__`/`__repr__`/`__eq__`; the mutable parameter-object choice (Ch 3)
**Default argument** — a fallback declared in the signature; replaces short-circuiting and documents the expected type (Ch 2)
**Dependency Inversion Principle (DIP)** — "Depend upon abstractions, not concrete details" (Ch 8)
**DRY** — Don't Repeat Yourself; one authoritative place for each piece of logic (Ch 9)
**Duck typing** — satisfying a contract by having the right methods, with no declared relationship (Ch 7, Ch 8)
**Dummy/stub implementation** — a no-op or `NotImplementedError` method written only to satisfy an abstract member; "useless code that we will need to maintain" (Ch 7)
**`Echo`** — the guide's class implementing "just the write method of the file-like interface"; returns instead of buffering (Ch 8)
**Explanatory variable** — a name given to a sub-part of an opaque expression (Ch 2)
**Fat interface** — an ABC bundling capabilities no single implementer needs in full (Ch 7)
**`field(default_factory=dict)`** — the dataclass idiom for a safe mutable default (Ch 5)
**File-like interface** — the informal `read`/`write`/`seek`/`truncate` protocol (Ch 8)
**Flag parameter** — a boolean argument selecting a code path; "tell your user that this function does more than one thing" (Ch 3)
**Generalization** — replacing sibling types with one supertype the consumer can serve, e.g. `Developer` + `Manager` → `Employee` (Ch 9)
**Generator** — a lazy iterator, e.g. `(c for c in clients if c.active)`; the "Even better" tier for filtering (Ch 3)
**`global` keyword** — the explicit marker of module-level mutation; "changing the meaning of the following line" (Ch 3)
**Guidelines, not laws** — "Not every principle herein has to be strictly followed" (Ch 1)
**History property** — a constraint on how an object's state may legally change over time (Ch 6)
**Hook method** — a small single-purpose method existing to be overridden, e.g. `render_body()` (Ch 5)
**Interface Segregation Principle (ISP)** — "Keep interfaces small so that users don't end up depending on things they don't need" (Ch 7)
**Invariant** — a property always true of an object (Ch 6)
**"Java-esque" tier** — bundling parameters into an untyped `dict`; better than 4 positional args, worse than any typed option (Ch 3)
**Level of abstraction** — the altitude of a statement: orchestration vs mechanics (Ch 3)
**Liskov Substitution Principle (LSP)** — functions using base-class references "must be able to use objects of derived classes without knowing it" (Ch 6)
**Magic number** — an unexplained literal; hoist to a module-level constant (Ch 2)
**Mental mapping** — forcing the reader to translate a short name into the concept it stands for (Ch 2)
**Mixin** — a bare-bones class mixed into a target via multiple inheritance; inherits `object`, placed before the target, never instantiated alone (Ch 5)
**Module-level constant** — an `UPPER_SNAKE_CASE` module name; home for hoisted magic values (Ch 2)
**MRO (method resolution order)** — the order Python searches bases; why mixin position matters (Ch 5)
**`mypy`** — the type checker this adaptation uses as its enforcement mechanism (Ch 1, Ch 3, Ch 6)
**Named capture group** — `(?P<name>...)` in a regex, read as `matches['name']` (Ch 2)
**`NamedTuple`** — the immutable, unpackable parameter-object choice (Ch 3)
**Near-miss duplication** — two nearly-identical units whose small differences motivated the copy (Ch 9)
**Open for extension** — new behaviour can be added by writing a new subtype (Ch 5)
**Open/Closed Principle (OCP)** — "Incorporate new features by extending the system, not by making modifications" (Ch 5)
**Parameter object** — a `dataclass`/`NamedTuple`/`TypedDict` bundling related arguments into one reusable entity (Ch 3)
**Property method** — `@property`; exposes a derived value as an attribute instead of a `get_*` function (Ch 2, Ch 3)
**Public-facing protocol** — the signatures a consumer may rely on; what `mypy` compares across an inheritance edge (Ch 6)
**Reason to change** — an external force that would compel an edit; the unit of responsibility (Ch 4)
**Reusability dividend** — an extracted unit becoming useful elsewhere; evidence the split followed a real seam (Ch 4)
**Searchable name** — a name that can be grepped; the reason to hoist literals to constants (Ch 2)
**Side effect** — anything a function does other than take values in and return values out (Ch 3)
**Signature incompatibility** — the concrete Python LSP breach: an override adding, removing, or retyping a parameter (Ch 6)
**Single Responsibility Principle (SRP)** — "A class should have only one reason to change" (Ch 4)
**Single point of update** — the property a good abstraction buys (Ch 9)
**Streaming response** — a response whose body is produced lazily from an iterator (Ch 8)
**Substitutability** — a subtype usable wherever the supertype is expected, with no call-site change (Ch 6)
**Template Method pattern** — fixed algorithm plus overridable step; `get()` + `render_body()` (Ch 5)
**3 Rs (readable, reusable, refactorable)** — the guide's stated quality standard (Ch 1)
**`typing.Protocol`** — structural typing; declares a duck-typed contract so `mypy` can verify it (Ch 7, Ch 8)
**`# type: ignore`** — pragma silencing `mypy`; used in the guide only to keep deliberately-bad examples in CI (Ch 3, Ch 6)
**Type hint** — an annotation, e.g. `current_date: str`, stating a type so the name needn't encode it (Ch 2)
**`TypedDict`** — Python 3.8+ parameter object with dict ergonomics and type checking; all keys required (Ch 3)
**Unneeded context** — repeating the enclosing class's name inside its own attribute names (Ch 2)
**Vocabulary consistency** — one noun per entity across all names that refer to it (Ch 2)
