# Glossary — clean-code-swift

**3 Rs (readable, reusable, refactorable)** — the guide's stated quality bar for Swift code (Ch 1)
**Adapter** — a type wrapping one request mechanism behind a common method, e.g. `SwiftAdapter.request(url:)` (Ch 7)
**`Any` / `as?`** — Swift's untyped escape hatch and the conditional downcast that follows it; the Bad type-checking pattern (Ch 4)
**Argument label** — the external parameter name in a Swift call, e.g. `createMenu(viewData:)`; used throughout the guide, never discussed by a rule (Ch 3)
**`async` / `await`** — marks a function that can suspend (`func f() async`) and each suspension point; replaces completion handlers (Ch 9)
**Backing store** — a `private` stored property (`_name`) behind a public computed property (Ch 5)
**Business-logic comment** — a comment explaining non-obvious reasoning or rules, the only kind the guide keeps (Ch 11)
**Change marker** — a banner comment dividing code into sections, `// MARK: -` included; the guide says avoid them (Ch 11)
**Commented-out code** — disabled code kept in the file; delete it, version control keeps it (Ch 11)
**Completion handler** — a closure called when asynchronous work finishes; the Bad concurrency shape (Ch 9)
**Composition** — building a type from other types held as properties (`Employee.taxData`) (Ch 6)
**Computed property (`get`/`set`)** — Swift's built-in getter/setter; validation can be added without changing call sites (Ch 5)
**Coupling** — how much one module must know about another; "makes your code harder to refactor" (Ch 8)
**Coverage (statements and branches)** — the share of code paths tests execute; the guide's target is 100% (Ch 9)
**Dead code** — a declaration nothing calls; delete it (Ch 4)
**Default argument** — a fallback value in the signature, used when the caller omits the argument (Ch 3)
**Dependency Injection (DI)** — passing a dependency in (here through `init`) instead of constructing it; the guide's means to DIP (Ch 8)
**Dependency Inversion Principle (DIP)** — high-level modules and details both depend on abstractions; abstractions don't depend on details (Ch 8)
**`@discardableResult`** — attribute silencing the unused-result warning on a chainable method (Ch 6)
**`do` / `try` / `catch`** — Swift's error-handling block (Ch 9)
**Enum case comparison** — `car.engine == .v8`; a compiler-checked replacement for string comparison (Ch 5)
**Explanatory variable** — a named constant for a sub-part of an opaque expression (`city`, `zipCode`) (Ch 2)
**Extension** — adds members to an existing type, including types you don't own; collision-prone on shared types (Ch 4)
**Fat protocol** — a protocol bundling requirements no single conformer needs in full (`Styling`) (Ch 8)
**Flag parameter** — a `Bool` selecting a code path; "the function does more than one thing" (Ch 3)
**Fluent interface** — chained mutators that return `self`, e.g. `car.setColor("pink").save()` (Ch 6)
**Force unwrap (`!`)** — asserts a non-`nil` optional and traps at runtime otherwise; a *Risk of Runtime Errors* (Ch 2)
**Functional style** — `map`/`filter`/`reduce` over accumulator loops; "Swift… has a touch of functional in it" (Ch 4)
**Gauss sum** — `n * (n + 1) / 2`; the guide's example of a fact worth a comment (Ch 11)
**`guard`** — early exit when a precondition fails (Ch 4, Ch 10)
**Interface Segregation Principle (ISP)** — "Clients should not be forced to depend on interfaces they do not use"; applied through protocols (Ch 8)
**"Is-a" vs "has-a"** — the inheritance test: subclass only for "is-a"; hold a property for "has-a" (Ch 6)
**JavaScript carryover** — text or code surviving the port from clean-code-javascript that is false in Swift (Ch 1)
**Labelled tuple** — `(firstName: String, lastName: String)`; returns several values without a global (Ch 4)
**Level of abstraction** — the altitude of a statement: parse the input vs call `database.save` (Ch 3)
**Liskov Substitution Principle (LSP)** — base and derived types "can be used interchangeably without getting incorrect results" (Ch 7)
**Magic number** — an unexplained literal such as `86400000` (Ch 2)
**`// MARK:`** — Xcode's section comment; a change marker by this guide's rule (Ch 11)
**Memberwise initializer** — the initializer Swift synthesizes for a struct's stored properties (Ch 3)
**Mental mapping** — making the reader remember what a short name (`l`) stands for (Ch 2)
**Method chaining** — mutators that `return self` so calls chain (Ch 6)
**Nil-coalescing (`??`)** — `a ?? b`; the Bad way to supply a parameter default (Ch 3)
**One concept per test** — each test method checks one behaviour (Ch 9)
**Open/Closed Principle (OCP)** — "open for extension but closed for modification" (Bertrand Meyer) (Ch 7)
**Optional binding (`if let`)** — unwraps an optional into a named constant only if it has a value (Ch 2)
**Optional stored property** — `var taxData: EmployeeTaxData?`; a composed part that may not exist yet (Ch 6)
**Parameter object** — a `struct` bundling related arguments (`MenuViewData`) (Ch 3)
**Polymorphism** — each type implements one method its own way, so callers don't branch (Ch 4, Ch 7)
**Predicate function** — a named `Bool` function for a compound condition (`shouldShowSpinner`) (Ch 4)
**`private`** — access control limiting a member to its enclosing declaration (Ch 5, Ch 6)
**Protocol** — a named set of requirements types declare conformance to; Swift's interface (Ch 8)
**Protocol-typed parameter / property** — `vehicle: Vehicle`, `styleConfig: StyleConfigurable`; depends on the abstraction (Ch 4, Ch 8)
**Pure object** — one that shares no mutable state; its changes return new instances (`refuel(amount:) -> Spaceship`) (Ch 5)
**Reason to change** — the unit of responsibility in SRP (Ch 7)
**Searchable name** — a named constant that can be found by search (Ch 2)
**Side effect** — anything a function does besides returning a value (Ch 4)
**Single effect owner** — the "one and only one" service allowed to perform an effect (Ch 4)
**Single Responsibility Principle (SRP)** — "There should never be more than one reason for a class to change" (Ch 7)
**Square/Rectangle problem** — a subclass overriding setters to keep its invariant, breaking the base type's callers (Ch 7)
**String dispatch** — choosing behaviour by comparing a name string; fails at runtime on a typo (Ch 7)
**SwiftLint** — the linter the guide recommends for formatting (Ch 10)
**`Task { … }`** — starts asynchronous work from synchronous code (Ch 9)
**Type tag** — a type encoded in a name (`currentDateStr`) (Ch 2)
**Unnecessary context** — repeating a type's name in its members (`User.userName`) (Ch 2)
**Value semantics** — structs and enums (`Array`, `String` included) copy on assignment; class instances are shared (Ch 4)
**Vocabulary consistency** — one word per concept (`getUser`, not User/Client/Customer) (Ch 2)
**Wet clay** — the guide's image of a first draft shaped by review (Ch 1)
**`XCTestCase` / `XCTAssertEqual`** — the XCTest class and assertion in the guide's tests (Ch 9)
