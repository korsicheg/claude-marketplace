# Clean Code — Glossary

**Abstract Factory** — creational pattern used to bury a `switch` so the rest of the system dispatches polymorphically, and to separate construction from use (Ch3, Ch11, Ch16)
**Active Record** — a data structure with public/bean variables plus `save`/`find`, usually a direct translation of a DB table; putting business rules on it creates a hybrid (Ch6)
**Adapter** — bridges your ideal interface to a foreign or not-yet-existing API (Ch8)
**Argument object** — a class wrapping variables that always travel together, replacing 3+ arguments (Ch3)
**Aspect / AOP** — modular construct declaring which points in a system get behavior modified for a cross-cutting concern, applied noninvasively (Ch11)
**Atomic operation** — an operation that is uninterruptable; 32-bit assignment is, 64-bit assignment and `++` are not (Ch13, App A)
**Boy Scout Rule** — leave the campground cleaner than you found it; improve something on every check-in (Ch1, Ch15, Ch16)
**Build-Operate-Check** — the three visible parts of a clean test (Ch9)
**Bound resource** — a fixed-size or fixed-count resource in a concurrent environment (Ch13)
**Bucket brigade** — making each function return what the next one needs, so temporal coupling cannot be violated (Ch17 G31)
**CAS (Compare and Swap)** — processor-level atomic update; optimistic locking, vs. `synchronized`'s pessimistic locking (App A)
**Code-sense** — the acquired ability to see not just that code is a mess, but the transformations that clean it (Ch1)
**Command Query Separation** — a function either does something or answers something, never both (Ch3)
**Critical section** — code that must be protected from simultaneous use for correctness (Ch13)
**Cross-cutting concern** — persistence, transactions, security, caching: concerns that cut across natural object boundaries (Ch11)
**Deadlock** — threads waiting on each other; requires mutual exclusion + lock & wait + no preemption + circular wait (Ch13, App A)
**Dependency Injection (DI)** — IoC applied to dependencies; the class is completely passive and receives them via constructor or setters (Ch11)
**Dependency Inversion Principle (DIP)** — depend on abstractions, not concrete details (Ch10)
**Dependency magnet** — a class (e.g. an error enum) that everything imports, forcing mass recompiles on every change (Ch3)
**Disinformation** — a name whose entrenched meaning differs from your intent, e.g. `accountList` for a non-List (Ch2)
**DRY / "Once, and only once"** — don't repeat yourself; the book's most emphasized rule (Ch3, Ch12, Ch17 G5)
**DTO (Data Transfer Object)** — a class with public variables and no functions; legitimate at boundaries (Ch6)
**Explanatory variable** — a named intermediate value that makes a calculation self-describing (Ch17 G19)
**Feature Envy** — a method more interested in another class's data than its own; sometimes a necessary evil (Ch6, Ch17 G14)
**F.I.R.S.T.** — Fast, Independent, Repeatable, Self-Validating, Timely (Ch9)
**Flag argument** — a boolean parameter; proof the function does more than one thing (Ch3, Ch17 F3)
**Hybrid** — half object, half data structure; the worst of both worlds (Ch6)
**Implicity** — the degree to which context is *not* explicit in the code itself (Ch2)
**Law of Demeter** — talk to friends, not to strangers; applies to objects, not data structures (Ch6, Ch17 G36)
**LeBlanc's Law** — *Later equals never* (Ch1)
**Learning test** — a test written to verify your understanding of a third-party API, kept as a regression check against new releases (Ch8)
**Livelock** — threads in lockstep, continually acting but never progressing (Ch13)
**Magic number** — any token whose value is not self-describing, including strings (Ch17 G25)
**Mental mapping** — forcing the reader to translate your name into the concept they know (Ch2)
**Newspaper metaphor** — headline name, high-level concepts at the top, detail increasing downward (Ch5)
**Niladic / monadic / dyadic / triadic / polyadic** — functions of 0/1/2/3/4+ arguments (Ch3)
**Noise words** — `Info`, `Data`, `Object`, `Variable`: distinctions without difference (Ch2)
**ONE SWITCH rule** — at most one switch per type of selection, and it must create polymorphic objects (Ch17 G23)
**Open-Closed Principle (OCP)** — open for extension, closed for modification (Ch10)
**POJO** — a plain object with no dependencies on enterprise frameworks or other domains (Ch11)
**Principle of Least Surprise / Astonishment** — implement the behavior another programmer would reasonably expect; put code where a reader expects it (Ch17 G2, G17)
**Reuse in the small** — extracting tiny commonalities, which raises visibility and enables larger reuse (Ch12)
**Rules of Simple Design (Beck's four)** — runs all tests; no duplication; expresses intent; minimizes classes and methods — *in that priority order* (Ch1, Ch12)
**Scope-length rule** — name length should be proportional to scope size (Ch2, Ch17 N5)
**Selector argument** — any argument (boolean, enum, int) used to pick behavior; a lazy substitute for splitting the function (Ch17 G15)
**Single Responsibility Principle (SRP)** — one, and only one, reason to change (Ch10)
**Special Case Pattern** — an object encapsulating the exceptional case, so client code never branches on it (Ch7)
**Starvation** — a thread prevented from proceeding for an excessively long time (Ch13)
**Stepdown Rule** — every function is followed by those one level of abstraction below it (Ch3)
**Temporal coupling** — an ordering dependency between calls; necessary sometimes, hidden never (Ch3, Ch17 G31)
**Template Method** — removes higher-level duplication where an algorithm is shared and one step varies (Ch12)
**TO paragraph** — phrasing a function as "TO do X, we do A, then B" to verify one level of abstraction (Ch3)
**Three Laws of TDD** — no production code without a failing test; no more test than suffices to fail; no more code than suffices to pass (Ch9)
**Train wreck** — chained calls like `a.getB().getC().doSomething()` (Ch6, Ch17 G36)
**Ubiquitous language** (Evans) — the team's shared project vocabulary, used in code (Ch17 N3)
**Wading** — slogging through bad code hunting for the thread of what it does (Ch1)
